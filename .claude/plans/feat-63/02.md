# Plan: Core Apparatus & Bash Tool Execution Roadmap

## Context

The 12-Factor Agent Core module (`source/core/`) was recently built across 12 user stories (US-001 through US-012). All primitives are complete and tested: schemas, agent loop, model interface, tool registry, bash tool, human-in-the-loop, middleware, context builder, thread, prompt templates, and error handling.

**The problem:** The core module is entirely self-contained — it is NOT integrated into the main CLI. `chat.tsx` still uses ad-hoc React-hook-based orchestration for streaming, tool call detection, bash consent, and conversation continuation. Two parallel implementations exist for the same concerns.

**The outcome:** A dependency-ordered roadmap that wires the core agent apparatus into the CLI, unifies bash tool execution under the middleware pattern, and eliminates duplicated orchestration logic. The roadmap will be added to `README.md`.

### Phase 1A — Event Emitter Adapter (blocked by P0)

**Modify** `source/core/agent.ts` — add `runAgentStream()` (~80 lines)
**Create** `source/__tests__/core-agent-stream.test.ts`
**Modify** `source/core/index.ts` — export new function

**Problem:** `runAgent()` runs the full loop and returns final `AgentState`. The TUI needs real-time events (model responses, tool calls, tool results) as they happen.

**Approach:** Add `runAgentStream()` as an `AsyncGenerator<AgentEvent, AgentState>` that yields each event as it occurs. `runAgent()` becomes a thin wrapper that consumes the generator and returns the final state. No breaking changes.

```typescript
// New type
export type RunAgentStreamInput = RunAgentInput & {
  onEvent?: (event: AgentEvent, state: AgentState) => void | Promise<void>;
};

// New function — yields events, returns final state
export async function* runAgentStream(input: RunAgentStreamInput): AsyncGenerator<AgentEvent, AgentState> { ... }
```

**Verification:** New tests pass. Existing `core-agent.test.ts` passes unchanged (no regression). Example: mock model, confirm tool_call and tool_result events yield before done.

### Phase 1B — Bash Consent Middleware (blocked by P0)

**Create** `source/core/bash-consent-middleware.ts` (~70 lines)
**Create** `source/__tests__/core-bash-consent-middleware.test.ts`
**Modify** `source/core/index.ts` — export factory + types

**Problem:** `core/bash-tool.ts` calls `executeBash()` directly with no consent. The consent flow only exists in React (`useBashConsent` hook + `BashConsentPrompt` component). Core's `beforeToolExecution` middleware hook (agent.ts:462-483) is the right integration point but no consent middleware exists.

**Approach:** `createBashConsentMiddleware(handler)` factory. The handler is framework-agnostic:

```typescript
type ConsentHandler = (command: string, risk: CommandRisk, warnings: string[]) => Promise<ConsentDecision>;
type ConsentDecision = { approved: true } | { approved: false; reason: string };
```

Middleware activates only for `toolCall.name === 'bash'`. Uses existing `validateCommand()` and `assessCommandRisk()` from `lib/local-tools/security.ts`. Blocked commands return `false` (triggers "skipped by middleware" in agent.ts:469-481). Otherwise delegates to handler.

**Reuses:** `validateCommand()` and `assessCommandRisk()` from `source/lib/local-tools/security.ts`.

**Verification:** Tests cover: blocked commands, approved, denied, non-bash tools passthrough. Integration: wire into `runAgent` with mock model requesting bash, confirm handler is called.

### Phase 1C — Thread Filesystem Persistence (blocked by P0)

**Create** `source/core/thread-store.ts` (~70 lines)
**Create** `source/__tests__/core-thread-store.test.ts`
**Modify** `source/core/index.ts` — export types + factory

**Problem:** `thread.ts` has `serialize()`/`deserializeThread()` but no persistence layer. The CLI's `-t <thread-id>` flag sends the ID to the backend. For core-driven conversation continuation, threads must persist to disk.

**Approach:** Thin `ThreadStore` interface + `createFileThreadStore(dir)` factory. Default dir: `~/.ruska/threads/`. Operations: `save(id, thread)`, `load(id)`, `list()`, `delete(id)`. JSON files on disk.

```typescript
type ThreadStore = {
  save(id: string, thread: Thread): Promise<void>;
  load(id: string): Promise<Thread | null>;
  list(): Promise<string[]>;
  delete(id: string): Promise<void>;
};
```

**Reuses:** `thread.serialize()` and `deserializeThread()` from `source/core/thread.ts`.

**Verification:** Tests use temp directory. Roundtrip: create thread, append events, save, load, verify match. Edge: load non-existent returns null.

### Phase 2A — Agent Runner Factory (blocked by P1A + P1B + P1C)

**Create** `source/core/runner.ts` (~120 lines)
**Create** `source/__tests__/core-runner.test.ts`
**Modify** `source/core/index.ts` — export runner

**Problem:** After Phase 1, all pieces exist but aren't wired together. The CLI commands need a single entry point that configures the model, tools, middleware, and thread from CLI-level options.

**Approach:** `createAgentRunner(config)` factory:

```typescript
type AgentRunnerConfig = {
  service: StreamServiceInterface;
  model?: string;
  assistantId?: string;
  threadId?: string;
  systemPrompt: string;
  maxIterations: number;
  maxErrors: number;
  enableBash: boolean;
  autoApprove: boolean;
  bashTimeout: number;
  consentHandler?: ConsentHandler;
  threadStore?: ThreadStore;
};
```

Internally: creates `ToolRegistry` (optionally registers bash), creates `MiddlewareStack` (optionally adds consent middleware), creates `ModelInterface` via `createStreamModel()`, calls `runAgentStream()`. If `threadId` provided, loads from `ThreadStore` and seeds events.

**Reuses:** `createStreamModel()` from `source/core/model.ts`, `registerBashTool()` from `source/core/bash-tool.ts`, `createBashConsentMiddleware()` from Phase 1B, `createFileThreadStore()` from Phase 1C.

**Verification:** Integration tests with mock model + mock consent handler. Test: bash-enabled + consent called. Test: auto-approve bypasses prompt. Test: thread ID loads and continues.

### Phase 3A — TUI Integration (blocked by P2A)

**Modify** `source/commands/chat.tsx` — rewrite `ChatCommandTui` (lines 153-529)

**Problem:** `ChatCommandTui` has ~375 lines of ad-hoc orchestration: manual tool call detection (useEffect at line 245), continuation requests (line 342-366), bash consent state management (useBashConsent), processed tool call tracking. All of this is now handled by the core runner.

**Approach:** Replace with:
1. Call `createAgentRunner()` with a `consentHandler` that resolves via React state (prompts user, resolves Promise on approve/deny).
2. Iterate the event stream, update React state on each event for rendering.
3. Keep existing presentation components (`BashConsentPrompt`, `BashBlockedPrompt`, `BashResultDisplay`) — they are pure UI.
4. Remove: `useBashConsent` usage, manual tool call detection useEffect, `continueConversation()`, `processedToolCalls` state, `continuationRequest` state.

**Net effect:** ~150 line reduction in chat.tsx. Orchestration logic consolidated in core.

**Verification:** `npm run build` + `npm run test:unit`. Manual tests:
- `ruska chat "list files" --bash` — consent prompt shown, execution works
- `ruska chat "list files" --bash --auto-approve` — auto-approve works
- `ruska chat "follow up" -t <thread-id>` — continuation works
- `ruska chat "hello"` — normal streaming works
- `ruska chat "hello" | cat` — auto-detects JSON mode

### Phase 3B — JSON Mode Integration (blocked by P2A)

**Modify** `source/commands/chat.tsx` — rewrite `runJsonMode()` (lines 535-623)

**Problem:** `runJsonMode()` is a completely separate code path that doesn't use core at all. It also ignores tool calls entirely (line 584: "NOTE: Ignoring tool_calls per requirements").

**Approach:** Replace with core runner usage. Map `AgentEvent` types to existing NDJSON format: `model_response` → `{type: "chunk"}`, `done` → `{type: "done"}`, `tool_result` → `{type: "tool_result"}`. Consent handler: auto-approve if `--auto-approve`, otherwise deny (no interactive prompt in piped mode).

**Net effect:** ~40 line reduction. Enables bash tool execution in JSON mode (currently impossible).

**Verification:** `ruska chat "list files" --json --bash --auto-approve | jq .` — NDJSON with tool results.
